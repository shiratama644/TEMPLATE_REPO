# Sandbox Constraints — 環境制約と迂回策

> 制約は派生プロジェクトやセッションごとに異なる。以下は起こり得る例であり、実測せず「この環境では不可」と決めつけない。確認した制約だけ `AGENTS.md §6.2` に記録する。

## 1. 確認すべき制約（環境ごとに検証）

| 兆候 | 確認・対処 |
|---|---|
| 外部 API や配布元への接続失敗 | URL・エラー・許可されるホストを確認する。ローカルではモック/固定データで純粋関数を検査し、実接続は未検証と報告する |
| ブラウザやネイティブツールが無い | 実機検証とモックの結果を分ける。使える CI がある場合のみ CI に委ね、skip を PASS と呼ばない |
| GitHub API の制限・権限エラー | `gh api` の状態とスコープを調べ、読み取り不足と書き込み拒否を区別する。許可なく権限を広げない |
| CI workflow を配置できない | 実際の権限エラーを確認してから利用者に手動配置を依頼する。存在しない代替ファイルを指さない |

## 2. 具体的な迂回パターン

### ネットワーク依存の処理

- Bun で GitHub API の TLS が `UNABLE_TO_VERIFY_LEAF_SIGNATURE` になり、Octokit の PR 参照が 500/unknown になる環境では、証明書検証を無効化せず `NODE_EXTRA_CA_CERTS=/etc/ssl/certs/ca-certificates.crt` を設定して再実測する。`gh api` が成功しても Bun の信頼ストアが同じとは限らない（PR レポートの実 API 再検証で確認）。

- 外部に依存しない部分（変換、入力の整形、純粋関数）は、ネットワークなしで単体テストする。
- 外部呼び出しの戻り値による分岐はモックで確かめる。実結合は「実環境検証待ち」としてタスクを分離する。
- Coverageはbaselineとbefore/afterを記録し、数字だけのshallow testを避ける。

### GPU・描画・画面を伴う処理

- 描画結果をテスト環境で再現しない。描画の前段（データ作成）と描画の処理を分離する。
- 目視確認は LIVE PREVIEW など利用者が見られる環境で行う。

### 決定論

- `step` やコアロジックに乱数・時計・I/Oを入れない。同じ入力なら同じ出力のテストを書く。

## 3. 復旧手順（Sandbox再構築時）

Sandbox再構築を検知したら（`git log` が起点1件のみ / 大量削除+未追跡 / 生成物ディレクトリ無）：

```bash
# 1. リモートの最新をfetch（ブランチ名は git branch --show-current で確認）
git fetch origin <現在のブランチ>

# 2. FETCH_HEAD の全ファイルと作業ツリーの内容・種類・実行権限を比較し、
#    余分な未追跡ファイルやローカル固有の変更がないと証明できた場合だけ実行。
#    一致しなければ停止して退避/相談（未コミット作業を消さない）。
git reset --hard FETCH_HEAD

# 4. 環境を再構築（AGENTS.md §6.1 のセットアップ手順に従う）
```

復旧後は必ず `git log --oneline -5` と §6.1 の検証コマンドで健全性を確認してから作業再開。

## 4. 検証キットの運用

ユーザーに実行させる検証キットを書く時のUXルール：

- `?probe=1` のようなクエリで軽量な疎通確認から始める
- 1 fetchで完結する設計
- 外部リトライはキット側で吸収
- raw URL + 自己チェック行を必ず含める（ユーザーがコピペで実行できる）
