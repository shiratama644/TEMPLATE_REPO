# Testing — 意味のある検証を設計するスキル

## 原則

- テストは「壊れたら困る振る舞い」を固定する。実装の写経をしない。
- カバレッジは目安。数字を上げるためだけの assert や、何も確かめない実行は書かない。
- 各機能に、正常系・境界値・異常系（空入力、不正入力、外部失敗）を最低 1 つずつ持たせる。
- テストを通すためにアサーションを緩める、スキップする、閾値を下げるのは禁止（AGENTS.md §3.2）。

## 分野ごとの読み替え（例）

| 分野 | 検証対象 | 典型的な方法 |
| :--- | :--- | :--- |
| ソフトウェア（ライブラリ・API・CLI） | 関数・エンドポイント・コマンドの入出力 | 単体テスト、契約テスト、統合テスト |
| データ・分析 | 集計値、件数、変換前後の合計 | 再現実行、突き合わせ、スキーマ検証 |
| 文書・文章 | 内部リンク、用語、表記、目次 | 内部リンク検査（`make links`）、用語集との照合 |
| 設定・インフラ | 設定の構文、適用前後の差分 | 構文チェック、dry-run / plan による差分確認 |

## 配置と命名

- テストは対象と対応する場所に置く（例: `tests/` 配下に同じ階層を作る）。プロジェクトの流儀が決まっていれば、それに従う。
- 1 テスト 1 振る舞い。名前は「何をしたら何が起きるか」が読める形にする。
- テストの実行は一回実行のコマンドを使う。監視モード（watch）は commit 前の検証に使わない。

## 意味のあるアサーション

弱い例（何も保証しない）:

```text
result = run(input)
assert result is not None        # 値の中身を見ていない
```

強い例（振る舞いを固定する）:

```text
result = run(input)
assert result == expected_output  # 期待値を具体的に書く
assert result.errors == []        # 副作用や警告も確認する
```

- 期待値は実装の出力を貼り付けて作らない。仕様や手計算から導く。
- 異常系は「失敗すること」だけでなく、どの失敗かを確認する。

## モックの範囲

- モックするのは **外部の境界だけ**: ネットワーク、現在時刻、乱数、外部 API、ファイルシステム、他プロセス。
- 自分のコードの内部は実物を使う。内部を全部モックすると、テストは実装の写しになる。
- モックは「どう呼ばれるべきか」（引数・回数・順序）を確認する。戻り値を都合よく固定して、検証を回避しない。

## カバレッジの運用

1. **baseline**: 現状の数値を記録する（AGENTS.md §6.1 または docs に）。
2. **ratchet**: 数値を下げない。新規コードは目標値を満たすよう求める。
3. **除外は理由付きで最小限**: 除外した箇所と理由を記録する。
4. 目標値そのものは、プロジェクトの状況に合わせて AGENTS.md §6.1 に決める。テンプレートは特定の数値を前提にしない。

## フレーキーテスト

- 時刻・順序・並列・外部状態に依存するテストは、失敗が再現できる形にする（時刻や乱数を注入する、順序を固定する）。
- 「再実行したら通った」で済ませない。原因を特定し、直すか、無効化の理由を残して隔離する。

## よくある失敗

- 件数やカバレッジだけを見て、何も確かめないテストを増やす。
- 内部のモックが多すぎて、本物の不具合を検出できない。
- テスト間で状態を共有し、実行順序で結果が変わる。
- 失敗したテストを削除して「全部通った」と報告する。
