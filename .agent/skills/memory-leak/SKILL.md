# Memory Leak — リソースの解放漏れを防ぐスキル

## 潜在的なリーク箇所

「登録したら解除する」対になる操作で、解除が抜けると漏れる。

| 登録 | 解除 |
| :--- | :--- |
| `open` / `acquire` | `close` / `release` |
| `subscribe` / `addListener` | `unsubscribe` / `removeListener` |
| `setInterval` / スレッドの起動 | `clearInterval` / スレッドの停止・join |
| 一時ファイルの作成 | 削除（終了時・失敗時の両方） |
| マップやキャッシュへの追加 | 削除、または上限付きの退避 |

## 修正パターン

### 所有者が終了時に全部解放する

- 子が登録したものは、親（所有者）の終了処理でまとめて解放する。
- 解放の入口は一つにする（例: `dispose()` や `close()` の中で全部行う）。

### 解放を言語の仕組みに任せる

- 後始末を保証する構文を使う（例: `try` / `finally`、`defer`、`with`、RAII、`using`）。
- 途中で例外や早期 return があっても、解放が必ず走ること。

### 上限付きの保持

- キャッシュや履歴は、件数や時間の上限を決めて古いものから捨てる。
- 「いつか使うかも」で無制限に溜めない。

## 回帰テスト

- 生成と破棄を繰り返し、終わった後に件数（登録数、ハンドル数、タイマー数）が元に戻ることを確かめる。
- 例外が起きた経路でも解放されることを確かめる。

## 監査（grep の例）

```text
# 登録と解除の数を比べる（件数が大きく違えば要確認）
grep -rn "addEventListener" src/ | wc -l
grep -rn "removeEventListener" src/ | wc -l

# 所有者の終了処理に解除が現れるか
grep -rn "dispose\|close\|release" src/
```

- grep は目安。対応関係を確かめるのは人かレビューで行う。

## よくある失敗

- 終了処理を書いたが、例外経路では呼ばれない。
- 購読者を登録したまま、対象が消えても参照が残る。
- キャッシュに上限が無く、長時間の運用で増え続ける。
- 解放の確認テストが無く、リファクタリングで静かに漏れる。
