# Rule 04: 検証・品質保証ルール

> 優先度: **HIGH** — 「できた気がする」で終わらせず、定義された手段で機械的に品質を担保する

## 1. 検証手段の実行（必須）

- プロジェクトで**定義された**検証手段のみを使う（存在しないコマンドを捏造・実行しない）。
- 検証手段の正本は `AGENTS.md §6.1`（検証コマンド）。未記録なら先にユーザーへ確認する。
- commit 前に、記録済みの検証をすべて PASS させる。
- 分野ごとの例:

| 分野 | 最低限の検証 |
| :--- | :--- |
| ソフトウェア | 型・静的解析 / 単体テスト（一回実行） / ビルド |
| ドキュメント | リンク切れ・目次整合性・表記ゆれ |
| データ / 分析 | スキーマ検証 / 再実行で同じ結果になるか / 集計値の突き合わせ |
| 設定・インフラ | 構文チェック / dry-run・plan による差分確認 |

### 各検証の注意

- **テスト**: watch モードではなく、一回実行（run 相当）で行う。
- **ビルド・実行**: 環境起因の既知エラー（外部接続失敗等）が出ても exit code が 0 なら成功扱いでよい（既知事象は `AGENTS.md §6.2` に追記して引き継ぐ）。
- **環境上実行できない検証**（GUI・外部 API・特定ハードウェア等）は無理に回避せず、実行できなかった事実と理由を報告し、CI や人間の確認に委ねる。

## 2. エラー対応と品質維持

- エラー発生時はメッセージやスタックトレースから根本原因を特定し、最小限の範囲で修正する。
- **検証を通すためだけの不正な修正は厳禁**：
  - テストの削除・スキップ・アサーションの緩和
  - 型エラーを回避するための安易な回避（`any` 等）
  - Lint ルールの勝手な無効化・エラーの握りつぶし
- **既存仕様の尊重**：既存の検証が落ちた場合、「検証の方が間違っている」と即断せず、既存仕様を壊していないか確認する。

## 3. 既存バグの扱い

- **今回のタスクを妨げるバグ・目的達成に必要な不整合**：必要最小限の修正を行う（`AGENTS.md §1.3.2`）。
- **無関係な既存バグ**：勝手に修正せず、ユーザーに報告する。
- バグ修正時は、可能であれば再発防止の検証（回帰テスト等）を追加する。

## 4. 完了前の機械検証チェックリスト

### (A) 検証手段がすべて PASS

`AGENTS.md §6.1` に記録された手段を全て実行する。

### (B) 意図しない差分の確認

```bash
git status --short
git diff --stat
# 狙いではないファイルが含まれていないかを目視
```

### (C) 機密情報の混入チェック

```bash
git diff --cached --name-only | grep -E "^\.env"
# → 出力が0件であること
```

### (D) ドキュメント整合性

- `docs/` に追加・削除があれば `docs/README.md` の目次が更新されているか
- `docs/task-list.md` の証拠（コミット SHA / 検証結果 / 実測値）が記録されているか

## 5. 報告のテンプレート

作業完了時は以下で簡潔に報告：

1. **変更ファイル一覧**（パスのみ）
2. **検証結果**（各検証の PASS / FAIL と件数）
3. **意図的に変えた点と、目的達成のため自分で判断して追加した作業**（理由を区別して記録）
4. **残課題・人間判断を求める事項・実行できなかった検証**（理由付き。未確認を完了と書かない）
