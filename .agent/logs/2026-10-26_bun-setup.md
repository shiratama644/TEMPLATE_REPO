# Bun 版セットアップと検証基盤

> Date: 2026-10-26(JST) / Commit: 記録後に作成 / PR: 5

## 1. 指示内容

Bun 前提で Python 製プログラムを TypeScript に移し、検証・依存・Git フック・CI を Bun に統一する。`bun run setup [引数]` は対話式・非対話式に対応し、目的・言語・テンプレート・機能を選ぶ。`full` ブランチを参考に 7 プリセット・17 機能と TS/JS・Python・Go・Rust の生成候補を用意する。OS パッケージは個別承認、不要文書は案内のみ。

## 3. 判断と未検証項目

- `full` の pnpm 依存を取り込まず、選択肢・機能構成を Bun で作り直した。生成先の Python/Go/Rust アプリには標準の言語別ツールを使い、リポジトリ内の検査とセットアップは Bun に統一。
- npm パッケージの Bun 実行体 1.4.4 をリポジトリ外の `/home/user/.bun-test/` に用意して検証した。OS パッケージは一切導入していない。
- `bun x` はこの実行環境でも動くが `bunx` は独立コマンドとして存在しなかったため、生成スクリプトを `bun x` に統一。Next.js のビルドには `@types/node` が必要で、Next とその monorepo テンプレートへ追加した。
- OS パッケージの実インストール、macOS / Windows / Termux の実機挙動、Python/Go/Rust 生成先の依存導入と実行は未検証。実機と管理者権限が必要なため安全境界として BUNSETUP-4 に残す。
- GitHub Actions は push 後に結果を確認する。既存の trailer フックを無効化していない。フックの有効化が必要な環境では利用者が既存フックと手動統合する。

## 4. 次にすべきこと

- 固定ブランチに push した後、PR の CI を確認する。失敗すれば修正して再検証する。
- 派生プロジェクト側で必要に応じ、OS 別の実機確認と Python/Go/Rust の依存・実行テストを行う。文書・Agent スキルの削除は利用者が候補を確認して決める。

## 5. CI 差分検証の修正（追記）

PR #5 の最初の CI では Bun の導入と frozen install は成功したが、`tests/setup.test.ts` の OS 案内テストが失敗した。原因は runner に `cargo` が既にあり、必要な OS パッケージの案内を出さない正常動作をテスト側が失敗と判定したこと。子プロセスの `PATH` を一時ディレクトリだけに限定してツール未導入を再現するよう修正した。テストは sudo や OS インストールを実行しない。修正後、ローカルの 7 ゲートは PASS。CI 再実行を待つ。

## 6. CI の結果（追記）

修正コミット `502540c` の PR #5 で Bun の全ゲート、gitleaks、dependency-review の 3 チェックが PASS した。初回失敗は隠さず §5 に記録した。未検証の OS パッケージ実インストールと非 Linux 実機は BUNSETUP-4 に残る。
